# CP3 失败根因与 CP3.5 修复路线

## 结论

CP3 的主要失败不是某一个接口 bug，而是路线错了：系统为了演示效果做成了玩具链路，使用 mock/stub、规则兜底、页面占位和局部证明替代真实智能产品链路。这样既不能证明智能能力，也不能稳定支撑现场演示。

## 具体表现

- `docs/readable/cp3-test-evidence.md` 明确记录：CP3 证据不宣称真实 OCR/LLM/对象存储联机 E2E，Java 主动调用 Python FastAPI 未纳入完成范围。
- Python 侧曾用 stub/mocked 测试证明结构化字段稳定，但这不能证明真实 OCR、真实 LLM 和真实知识库调用可用。
- Java-Python 集成主要证明 Worker 轮询与回写，不是前端提交后 Java 主动调度 Python 的生产级链路。
- 前端结果页只展示材料元数据和抽取结果，缺少可安全嵌入的 PDF/图片预览地址，审批人员无法核验 AI 结论与原始材料。
- GLM OCR 实际联机时暴露出裸 base64 请求格式问题。说明此前验收没有覆盖真实 OCR 请求格式和真实外部服务响应。
- “规则结果 + 人工复核”式兜底会掩盖 Agent、OCR、MCP 或 RAG 失败，使系统看似有结果，实际不能证明智能审查能力。

## CP3.5 的修正原则

- 验收从真实链路开始设计，而不是先做页面演示再补逻辑。
- 真实材料、真实对象存储、真实 OCR、真实 LLM、真实 MCP、真实 Java-Python 调度必须共同出现在最终证据里。
- 外部智能依赖失败时，任务应失败、阻塞或待重试，并把原因暴露给审批人员/开发者；不能输出假结论。
- 自动化测试仍可使用 mock 做单元隔离，但最终 CP3.5 验收必须另有真实联机 E2E。
- 所有任务 PRD 都要围绕“让智能链路真实可用”展开，避免再次扩散到演示包装或 CP4 能力。

## 后续引用

本文件应被 CP3.5 父任务和各子任务的 `implement.jsonl` / `check.jsonl` 引用，用来防止后续实现重新退回演示玩具路线。
