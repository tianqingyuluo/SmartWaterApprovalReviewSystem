SmartWater MVP Domain Model and Contract Design
===============================================

Context and motivation
----------------------

SmartWater MVP needs a shared domain language before Java backend, Python Worker, frontend, regulation knowledge pack, and inference adapter work can proceed in parallel. This document defines the DDD model, task state machine, visibility boundaries, and first JSON contract draft for the MVP path: anonymous material submission -> async OCR/extraction/review -> applicant and reviewer result views.

Goals:

- Define the MVP bounded contexts and their responsibilities.
- Define canonical domain entities, value objects, enums, and status transitions.
- Define fixed material slots and file constraints for the first implementation.
- Define frontend-facing and Worker-facing JSON DTO/schema drafts.
- Define visibility differences between applicant result and reviewer result.
- Give downstream MVP tasks a stable first contract to implement against.

Non-goals for MVP:

- No account system, role login, reviewer task list, or workflow actions.
- No full approval process state machine such as acceptance, preliminary review, recheck, correction, completion.
- No material versioning, correction loop, multi-file slots, free upload classification, or multi-round resubmission.
- No final legal approval decision generated by AI.
- No full database schema or concrete Java/Python class implementation in this task.

Implementation considerations
-----------------------------

Design principles:

- Contract first: downstream tasks should reuse the enums and DTO shapes here instead of inventing parallel names.
- Java owns business state: submission records, material metadata, object storage references, task status, and result query APIs live behind the Java backend boundary.
- Python owns AI processing: OCR, field extraction, review reasoning, material summaries, and explainable result generation live behind the Worker boundary.
- Knowledge is evidence, not final decision logic: regulation entries and field rules guide review output, but the final decision remains human-owned.
- Visibility is explicit: applicant-facing output is a filtered projection of review results, not the same payload as the reviewer view.
- Partial success is first-class: missing materials, OCR failures, and reasoning failures must be expressible without discarding successful material results.

Key constraints:

- MVP supports exactly three fixed slots: application form, business license, and ID card.
- Each slot accepts at most one file.
- Accepted file types are `jpg`, `jpeg`, `png`, and `pdf`; `doc` and `docx` are out of scope.
- Missing materials do not block submission.
- MVP supports one applicant and one water source in the normalized model. If OCR sees additional applicants or sources, it should create a warning instead of expanding the domain model.
- Task ID and session token are enough for demo access; no authenticated user ID is required in MVP.

High-level behavior
-------------------

1. Applicant uploads zero to three files into fixed material slots.
2. Java backend validates slot names, file count per slot, content type/extension, and creates a review task.
3. Java backend stores material metadata and object storage references, then returns `taskId`, `sessionId`, and initial status.
4. Python Worker receives or pulls `taskId`, material references, and knowledge pack version.
5. Python Worker performs OCR per material, extracts structured fields, compares known fields and evidence, invokes review reasoning, and writes back a structured result.
6. Frontend polls task status and renders processing, partial success, failed, or completed states.
7. Applicant view shows only basic missing material and obvious field/upload hints.
8. Reviewer view shows full extracted fields, material summaries, issue list, risk hints, draft review opinion, evidence references, and manual review notes.

Bounded contexts
----------------

### Submission context

Owned by Java backend.

Responsibilities:

- Accept material uploads into fixed slots.
- Create review task identity.
- Persist task status, material metadata, object storage reference, and result snapshots.
- Serve applicant and reviewer result projections.

Core concepts:

- `ReviewTask`
- `MaterialSlot`
- `SubmittedMaterial`
- `TaskAccessToken`
- `ProcessingStatus`

### Document intelligence context

Owned by Python Worker.

Responsibilities:

- OCR material files.
- Extract application form fields and credential fields.
- Normalize extracted values into the contract schema.
- Return field-level confidence and evidence references.

Core concepts:

- `OcrResult`
- `ExtractedField`
- `ApplicantProfile`
- `ProjectProfile`
- `WaterSourceProfile`
- `CredentialProfile`

### Review assistance context

Owned by Python Worker, with model supplier chosen by inference vendor task.

Responsibilities:

- Generate AI-assisted issue list, risk hints, draft opinion, summaries, and manual review prompts.
- Keep output explainable by linking issues to fields, materials, and knowledge references.
- Mark output as assistance, not approval decision.

Core concepts:

- `ReviewFinding`
- `RiskHint`
- `DraftReviewOpinion`
- `MaterialSummary`
- `EvidenceReference`

### Regulation knowledge context

Owned by knowledge pack task.

Responsibilities:

- Provide static material checklist, field rules, review basis entries, and prompt snippets.
- Version knowledge inputs so generated results can record what basis was used.

Core concepts:

- `KnowledgePackVersion`
- `ChecklistItem`
- `FieldRule`
- `ReviewBasis`
- `PromptSnippet`

Canonical language
------------------

| Chinese term | English contract term | Meaning |
|---|---|---|
| 审核任务 | `ReviewTask` | One anonymous submission and one processing/result lifecycle |
| 会话 ID | `sessionId` | Demo access token used with task ID to query result |
| 材料槽位 | `MaterialSlot` | Fixed upload position for a known material type |
| 申请书 | `APPLICATION_FORM` | Water abstraction permit application form |
| 营业执照 | `BUSINESS_LICENSE` | Applicant organization credential |
| 身份证 | `ID_CARD` | Legal representative or applicant identity credential |
| 抽取字段 | `ExtractedField` | Structured value extracted from OCR/material content |
| 问题清单 | `ReviewFinding[]` | Missing, inconsistent, incomplete, or risky items |
| 风险提示 | `RiskHint[]` | Items requiring manual attention, not necessarily errors |
| 审核意见草稿 | `DraftReviewOpinion` | AI-assisted text for reviewer reference |
| 依据引用 | `EvidenceReference` | Link to field/material/knowledge item that supports a finding |

Enums and value constraints
---------------------------

### MaterialType

```json
["APPLICATION_FORM", "BUSINESS_LICENSE", "ID_CARD"]
```

Rules:

- `APPLICATION_FORM` is optional at upload time but required for complete review.
- `BUSINESS_LICENSE` is optional at upload time but required for organization consistency checks.
- `ID_CARD` is optional at upload time but required for legal representative/person identity consistency checks.
- Missing materials produce `MISSING_MATERIAL` findings; they do not fail the task by themselves.

### AcceptedFileType

```json
["jpg", "jpeg", "png", "pdf"]
```

Rules:

- Frontend and backend both validate extension and MIME type where available.
- `doc` and `docx` are rejected in MVP.
- One `SubmittedMaterial` per `MaterialType` maximum.

### ProcessingStatus

```json
[
  "SUBMITTED",
  "QUEUED",
  "PROCESSING",
  "PARTIAL_SUCCESS",
  "COMPLETED",
  "FAILED",
  "CANCELLED"
]
```

State meanings:

| Status | Meaning | Terminal |
|---|---|---:|
| `SUBMITTED` | Java accepted upload and persisted task metadata | No |
| `QUEUED` | Task is waiting for Worker processing | No |
| `PROCESSING` | Worker is processing OCR/extraction/review | No |
| `PARTIAL_SUCCESS` | Some materials or review steps succeeded and some failed | Yes for MVP result display |
| `COMPLETED` | OCR/extraction/review completed for all available materials | Yes |
| `FAILED` | No useful result can be produced due to system or input failure | Yes |
| `CANCELLED` | Reserved for future/manual cancellation; not expected in MVP UI | Yes |

Allowed transitions:

```text
SUBMITTED -> QUEUED
SUBMITTED -> PROCESSING
QUEUED -> PROCESSING
PROCESSING -> COMPLETED
PROCESSING -> PARTIAL_SUCCESS
PROCESSING -> FAILED
QUEUED -> FAILED
SUBMITTED -> FAILED
```

MVP does not support transitions from terminal states back to processing. A new upload attempt creates a new task.

### FindingType

```json
[
  "MISSING_MATERIAL",
  "MISSING_FIELD",
  "INVALID_FORMAT",
  "INCONSISTENT_IDENTITY",
  "INCONSISTENT_CREDENTIAL",
  "WATER_SOURCE_INCOMPLETE",
  "WATER_AMOUNT_REVIEW_REQUIRED",
  "PERMIT_REQUIREMENT_REVIEW_REQUIRED",
  "PUBLIC_NOTICE_REVIEW_REQUIRED",
  "WATER_RESOURCE_ASSESSMENT_REVIEW_REQUIRED",
  "MULTI_APPLICANT_UNSUPPORTED",
  "MULTI_WATER_SOURCE_UNSUPPORTED",
  "OCR_LOW_CONFIDENCE",
  "MODEL_UNCERTAIN",
  "SYSTEM_ERROR"
]
```

### Severity

```json
["INFO", "WARNING", "BLOCKER"]
```

Rules:

- `BLOCKER` means the reviewer should not rely on AI output until manual review addresses the item.
- `WARNING` means review attention is needed but partial result remains useful.
- `INFO` means explanatory or low-risk hint.

### Audience

```json
["APPLICANT", "REVIEWER", "SYSTEM"]
```

Rules:

- Applicant projection includes findings where `visibleTo` includes `APPLICANT`.
- Reviewer projection includes all `REVIEWER` findings and may include applicant-visible findings.
- `SYSTEM` items are for logs/debug status and should not be shown directly without mapping.

Core aggregate model
--------------------

### ReviewTask aggregate

Aggregate root: `ReviewTask`.

Fields:

| Field | Type | Required | Notes |
|---|---|---:|---|
| `taskId` | string | Yes | Public task identifier, unique and non-guessable enough for demo |
| `sessionId` | string | Yes | Access token paired with `taskId` |
| `status` | `ProcessingStatus` | Yes | Current processing state |
| `submittedAt` | ISO-8601 datetime | Yes | Backend server time |
| `updatedAt` | ISO-8601 datetime | Yes | Last state/result update time |
| `materialSlots` | `MaterialSlot[]` | Yes | Always contains three fixed slots |
| `resultSummary` | `ResultSummary` | No | Lightweight status/result counts |
| `applicantResult` | `ApplicantResult` | No | Filtered applicant projection |
| `reviewerResult` | `ReviewerResult` | No | Full reviewer projection |
| `knowledgePackVersion` | string | No | Version/hash used by Worker |

Invariants:

- A task has exactly one lifecycle.
- A task can contain zero to three submitted materials.
- A task cannot mutate submitted material files after processing starts in MVP.
- Terminal state does not imply legal approval or rejection.

### MaterialSlot

Fields:

| Field | Type | Required | Notes |
|---|---|---:|---|
| `materialType` | `MaterialType` | Yes | Fixed enum |
| `displayName` | string | Yes | Chinese display label |
| `requiredForCompleteReview` | boolean | Yes | `true` for all MVP slots |
| `maxFiles` | integer | Yes | Always `1` in MVP |
| `acceptedFileTypes` | string[] | Yes | `jpg/jpeg/png/pdf` |
| `material` | `SubmittedMaterial` | No | Present if uploaded |
| `missing` | boolean | Yes | Derived from material presence |

### SubmittedMaterial

Fields:

| Field | Type | Required | Notes |
|---|---|---:|---|
| `materialId` | string | Yes | Backend material identifier |
| `materialType` | `MaterialType` | Yes | Must match slot |
| `originalFileName` | string | Yes | Sanitized display name |
| `contentType` | string | Yes | MIME type when available |
| `fileExtension` | `AcceptedFileType` | Yes | Lowercase extension |
| `fileSizeBytes` | integer | Yes | Positive integer |
| `storageObjectKey` | string | Yes | Internal only; not exposed to applicant/reviewer by default |
| `uploadedAt` | ISO-8601 datetime | Yes | Backend server time |
| `processingStatus` | `MaterialProcessingStatus` | Yes | Per-material processing state |

### MaterialProcessingStatus

```json
["PENDING", "OCR_PROCESSING", "EXTRACTION_PROCESSING", "SUCCEEDED", "FAILED", "SKIPPED"]
```

Rules:

- Missing slots do not create `SubmittedMaterial`; they appear as `missing = true`.
- `SKIPPED` is reserved for processing steps skipped because prerequisites failed.

Field value object
------------------

`ExtractedField` is used for every normalized field.

```json
{
  "value": "张三",
  "normalizedValue": "张三",
  "source": "APPLICATION_FORM",
  "confidence": 0.91,
  "evidenceRefs": ["evidence_001"]
}
```

Rules:

- `value` is the human-readable extracted value.
- `normalizedValue` is optional and should be used when the Worker normalizes dates, numbers, enums, or identifiers.
- `confidence` is a float from `0` to `1`, or `null` when unavailable.
- `source` must be one of `MaterialType`.

API contract draft
------------------

Endpoint names are draft names for downstream backend/frontend tasks. They may be adjusted during implementation, but response semantics should remain stable.

### Submit materials

`POST /api/mvp/review-tasks`

Request: multipart form data.

Fields:

| Form field | Required | Notes |
|---|---:|---|
| `applicationForm` | No | One file, maps to `APPLICATION_FORM` |
| `businessLicense` | No | One file, maps to `BUSINESS_LICENSE` |
| `idCard` | No | One file, maps to `ID_CARD` |

Visibility and privacy contract
-------------------------------

Applicant may see:

- Submitted/missing materials.
- Basic upload or OCR quality hints.
- Obvious missing field hints.
- Suggested next actions such as re-upload or supplement material.

Applicant must not see:

- Full draft review opinion.
- Full risk analysis.
- Internal model uncertainty reasoning.
- Reviewer-only manual review prompts.
- Object storage keys or internal material IDs when not needed.

Reviewer may see:

- All normalized profiles and material summaries.
- Findings, risk hints, draft review opinion, evidence references, and manual review prompts.
- AI disclaimer and confidence indicators.

System/internal only:

- Storage object keys.
- Provider raw response payloads.
- Secrets, API keys, request signatures, and internal callback URLs.

Error handling and UX
---------------------

Error categories:

| Category | Example | User effect |
|---|---|---|
| User input error | Unsupported `docx` upload | Submission rejected with clear message |
| Missing material | No business license uploaded | Submission accepted; missing material finding generated |
| OCR failure | Provider timeout for one material | `PARTIAL_SUCCESS` if other materials produce results |
| Reasoning failure | Model output invalid JSON | Basic extraction result can still show; reviewer sees AI reasoning failure |
| Storage/system failure | Object storage unavailable | Submission or processing fails with retryable system error |

UX messages:

- Use neutral wording: “需要人工复核” instead of “不合格”.
- Always display AI assistance disclaimer on result pages.
- For terminal `FAILED`, show a retry/re-submit suggestion without exposing internal provider details.
- For `PARTIAL_SUCCESS`, show available results and clearly mark unavailable sections.

Lifecycle and update cadence
----------------------------

- A task is immutable after submission in MVP.
- A new upload creates a new task instead of modifying an existing task.
- Frontend polling interval should be decided by frontend/backend tasks, but status endpoint must support repeated reads.
- Worker can update status multiple times before sending final result.
- Knowledge pack version used for a task must be recorded on the task result.

Future-proofing
---------------

The MVP contract intentionally leaves expansion points:

- `ApplicantProfile` can later become `ApplicantProfile[]` for共同申请人.
- `WaterSourceProfile` can later become `WaterSourceProfile[]` for多水源.
- `SubmittedMaterial` can later support `fileGroupId` or multiple files per material type.
- `ReviewTask` can later link to authenticated users and workflow instances.
- `ProcessingStatus` can later be mapped to richer approval workflow states without changing MVP terminal meanings.
- `ReviewBasis` references can later point to a managed knowledge base instead of static config.

Breaking changes to avoid:

- Renaming `MaterialType` enum values after backend/Worker/frontend implementation starts.
- Returning reviewer-only fields in applicant result.
- Treating AI draft opinion as final approval result.
- Making missing materials block task creation.

Implementation outline for downstream tasks
-------------------------------------------

1. Backend task:
   - Implement `ReviewTask`, `MaterialSlot`, `SubmittedMaterial`, status persistence, submit/status/result APIs, and Worker callback boundary.
2. Knowledge pack task:
   - Produce material checklist, field rules, review basis IDs, and prompt snippets using the enum names here.
3. Inference vendor task:
   - Define adapter output that maps directly to `ReviewFinding`, `RiskHint`, `DraftReviewOpinion`, and `EvidenceReference`.
4. Python Worker task:
   - Implement OCR/extraction/review pipeline and return the Worker result callback shape.
5. Frontend task:
   - Implement upload slots, polling states, applicant result projection, and reviewer result projection.
6. Spec hardening task:
   - Move stable pieces of this contract into `.trellis/spec/` after implementation validates them.

Testing approach
----------------

Contract tests needed downstream:

- Backend rejects unknown material slots and unsupported file types.
- Backend accepts missing materials and creates task with missing slot state.
- Backend prevents more than one file per slot.
- Worker result with one failed material maps to `PARTIAL_SUCCESS`.
- Applicant result excludes reviewer-only fields.
- Reviewer result includes findings, risk hints, draft opinion, and evidence references.
- Terminal statuses do not transition back to `PROCESSING` in MVP.
- Multi-applicant or multi-water-source detection produces warnings instead of expanding the MVP model.

Acceptance criteria
-------------------

- Core MVP bounded contexts and ownership boundaries are defined.
- Material type enum, file format constraints, and one-file-per-slot rule are defined.
- Task and material processing status enums are defined with allowed transitions.
- Applicant and reviewer result projections are distinct and testable.
- Java backend, Python Worker, frontend, knowledge pack, and inference adapter boundaries are defined.
- First JSON DTO/schema drafts exist for submit/status/result APIs and Worker input/result callbacks.
- Expansion points and forbidden breaking changes are documented for V1/V2.
