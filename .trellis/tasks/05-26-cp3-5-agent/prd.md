# CP3.5 生产级初审 Agent 修复任务组

## 定位

CP3.5 不是新增炫技功能，也不是 CP4 的提前实现。它是 CP3 的修复主线：把当前“为了演示而做的玩具链路”收回到生产级、全真实、可现场跑通的初审 Agent 产品链路。

CP3 失败的根因必须保留在任务上下文中：此前的系统用 mock/stub、轮询证明、规则兜底和页面占位拼出了“看起来像演示”的链路，但真实 OCR、真实 LLM、真实 MCP 工具调用、真实对象存储材料、真实 Java-Python 调度和真实前端证据查看没有形成闭环。结果不是降低风险，而是弄巧成拙：系统既不像生产系统，也不能稳定完成现场演示。

## 核心路线

目标链路必须按真实产品链路运行：

1. 申请人用真实账号上传真实 PDF/DOCX/图片材料。
2. Java 后端把材料保存到真实对象存储，创建审查任务，并主动调度 Python FastAPI。
3. Python 通过受控接口下载真实材料，执行格式识别、结构化解析和真实 OCR。
4. Agent 通过 MCP Client 发现并调用知识库、完整性检查等工具。
5. Agent 基于真实抽取文本、RAG 依据、规则配置和 LLM 推理生成结构化初审结论。
6. Python 回写 Java，Java 持久化状态、字段、问题、依据、模型元数据和错误。
7. 前端展示真实材料预览、OCR/抽取结果、合规问题、法规依据、修改建议和审批动作。
8. 验收使用真实中间件、真实外部 AI 调用、真实账号和真实材料，不用 mock 结果冒充成功。

## 硬约束

- 不接受演示专用假数据、假 OCR、假 LLM、假 MCP 调用或静态页面占位作为 CP3.5 验收结果。
- 不用“规则兜底”替代智能审查。外部 AI、OCR、MCP 或知识库不可用时，任务应进入明确失败/阻塞/待重试状态，而不是生成看似成功的审查结论。
- 可以保留重试、错误记录、可观测日志和人工介入入口；这些只用于解释失败与恢复，不用于伪造智能结果。
- 自动化测试可以 mock 外部依赖做单元测试，但 CP3.5 验收证据必须包含真实联机链路。
- 前端不得只展示抽取结果而没有原始材料证据；审批人员必须能对照原文、OCR 和 AI 结论。
- 不把 Worker token、对象存储密钥、原始 `storageKey` 或外部 API key 暴露给浏览器或文档。
- Git 版本控制证据按指导书口径准备到账号维度；不能用单一账号提交数冒充全组贡献。

## 评分项映射

| 检查项 | CP3.5 验收口径 |
| --- | --- |
| MCP 调用 | Agent 通过 MCP Client 发现并调用工具；日志和结果能证明工具调用发生，不是内部函数直连。 |
| 结构化文档处理 | PDF/DOCX 文本、表格、关键字段被真实解析，进入统一文本块和结构化字段。 |
| 非结构化文档处理 | 图片/扫描件走真实 OCR，成功结果进入 `extractedFields`，失败结果明确可见。 |
| 合规审查 | 基于真实抽取文本、RAG 依据和规则配置给出结论、原因、引用和修改建议。 |
| 结果稳定性 | 同一材料重复运行，关键结构化结论、问题编码和引用来源稳定。 |
| Java-Python 集成 | 前端提交 -> Java 调度 -> Python 审查 -> Java 回写 -> 前端展示全链路可运行。 |
| Git 版本控制 | 每个参评账号提交证据、关键提交说明和最终演示版本标签可追溯。 |

## 总体验收标准

- 一键或少步骤启动 Java、Python、Worker、前端、MySQL、RustFS、ChromaDB/MCP 相关服务。
- 至少三组真实样例可跑通：材料完整且基本合规、缺少材料、材料内容存在明显问题。
- 每组样例都能在前端看到原始材料预览、OCR/抽取结果、AI 结论、问题列表、依据和建议。
- 日志或审查详情可证明 Python 调用了真实 OCR、真实 LLM、真实 MCP 工具和真实 Java 回写接口。
- 禁用外部 AI/OCR/MCP 任一关键依赖时，系统展示明确失败/阻塞/待重试，不生成假通过结论。
- 复跑同一材料 3 次，关键结构化结果稳定；自由文本允许小幅变化但不能改变结论。
- `docs/readable/**` 中保留 CP3.5 真实验收证据、失败复盘、运行步骤和 Git 账号提交证据。

## 明确不做

- 不做 CP4 的材料补正版本差异、报告导出、部署答辩整包和生产运维面板。
- 不为了现场效果增加隐藏按钮、硬编码样例结论或页面静态截图。
- 不以单元测试 mock 成功替代真实联机 E2E。
