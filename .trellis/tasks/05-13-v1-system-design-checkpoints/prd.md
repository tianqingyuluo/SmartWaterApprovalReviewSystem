# V1 系统设计与检查点拆分

> 状态：brainstorm 进行中。本文只记录已确认决策和已读材料依据，不是最终设计初稿。

## Goal

在 MVP 基础上继续设计 SmartWater V1，并按课程检查点组织可分派、可验收的任务。V1 设计必须优先对齐 `docs/《方向模块课程实践》指导书.doc` 的评分节点，同时利用 `docs/参考资料/` 中的取水许可业务材料完善知识库、MCP、Agent、系统集成和答辩交付。

## Confirmed Decisions

### 1. 规划方式

采用混合组织：

* 以课程四个检查节点作为父级里程碑。
* 以系统模块作为可分派子任务。
* 汇报按评分点组织，开发按模块边界组织。

### 2. CP1 处理方式

项目基础架构搭建视为已由 MVP 基本完成。V1 不重做 CP1，只做验收映射和缺口确认。

CP1 后续只应产出：

* 课程评分项到现有 MVP 证据的映射。
* 少量缺口清单，例如团队分工、Git 提交证明、运行截图、接口截图。
* 若某项课程硬要求无法由 MVP 证明，再拆轻量补齐任务。

### 3. Python 服务形态

V1 采用 FastAPI 主导架构：Java 后端通过 HTTP 调用 Python AI 服务。

该决策意味着：

* Python 侧需要从现有 Worker 主动拉取模式，演进为可被 Java 调用的 AI 服务接口。
* 课程要求中的 FastAPI、Swagger、Java 调 Python、错误处理、系统集成应作为 V1 验收重点。
* 现有 Worker 代码可作为实现资产复用，但不再作为 V1 的主要架构叙事。

### 4. Java 调 Python 的任务模式

V1 采用异步任务接口：

* Java 调用 Python FastAPI 创建 AI 审查任务。
* Python 返回 `aiTaskId` 或等价任务标识。
* Java 后续查询 Python 任务结果，或由 Python 回调/回写 Java。
* 该模式优先保证大文件、OCR、RAG、LLM 调用的稳定性，避免同步 HTTP 长时间阻塞。

### 5. 异步结果回传方式

V1 采用 Python 主动回调/回写 Java：

* Java 创建 Python AI 审查任务时传入 Java 任务标识和回写契约。
* Python 完成 OCR、RAG、MCP、Agent 审查后调用 Java 接口回写结构化结果。
* Java 数据库继续作为前端查询和结果展示的事实源。
* Python 需要处理回写失败、重试、幂等和最终失败状态。

### 6. V1 知识库范围

V1 CP2 主线只覆盖课程指定参考资料：

* `docs/参考资料/取水许可办理需资料及流程.docx`
* `docs/参考资料/填报说明.docx`
* `docs/参考资料/国民经济分类国标.pdf`
* `docs/参考资料/申请书.docx`
* 证照样例：`营业执照.jpg`、`身份证.jpg`、`驾驶证.png`

不把申领表、验收申请、验收报告纳入 CP2 主线知识库范围；这些材料可作为 CP4 创新点或后续产品化扩展。

### 7. V1 材料上传范围

V1 采用“固定主槽位 + 自由附件区”：

* 固定主槽位继续沿用 MVP 三类材料：申请书、营业执照、身份证。
* 自由附件区允许上传其他补充材料，用于后续知识检索、Agent 审查或演示扩展。
* 驾驶证样例主要作为“文件名/槽位声称是身份证，但内容不是身份证”的负向测试材料。
* V1 不把申请报告、第三者利害关系说明、水资源论证等全部材料清单固化为独立槽位。
* 自由附件区 V1 不做自动材料分类；附件以未分类材料身份进入 OCR/RAG/Agent 审查，审查结果可以提示“无法确认材料类型”。

### 8. MCP Server 交付形态

V1 CP2 采用独立 MCP Server：

* Python 侧必须提供可单独启动的 MCP Server。
* MCP 工具列表必须可演示。
* 至少实现并暴露 `knowledge_search` 和 `check_completeness` 两个工具。
* FastAPI / LangChain Agent 可以通过 MCP 调用这些工具，但 CP2 验收以独立 MCP Server 为主。

### 9. 知识库 ingest 方式

V1 CP2 提供可重复运行的知识库 ingest 命令/API：

* 支持读取课程指定参考资料。
* 支持文档解析、分块、向量化和写入 ChromaDB。
* 支持重复运行，至少具备清空重建或幂等重建能力。
* 需要输出可用于验收的 ingest 日志或统计，例如文档数、分块数、向量条目数。

### 10. Embedding 模型来源

V1 CP2 采用外部 API Embedding 服务：

* 不以本地 HuggingFace 模型作为主线方案。
* Embedding API Key、base URL、模型名必须通过环境变量或配置文件注入，不写入 Git。
* ingest 命令/API 需要清晰暴露外部 API 调用失败、限流、超时等错误。
* 答辩或检查点演示需要提前准备可用 API Key 和网络环境；如需离线演示，应另行准备缓存数据或降级说明。

### 11. Embedding provider 配置方式

V1 为 Embedding 单独配置 provider，不复用 `REVIEW_LLM_*`：

* `EMBEDDING_PROVIDER`
* `EMBEDDING_MODEL`
* `EMBEDDING_BASE_URL`
* `EMBEDDING_API_KEY`

原因：

* 当前项目没有统一模型网关抽象，而是按能力分别配置 OCR 与审核推理模型。
* Embedding 与 Chat Completion 通常使用不同模型、不同能力边界，独立配置更清晰。
* 独立配置不会影响现有审核推理适配器。

### 12. CP3 Agent 审查输出

CP3 输出“辅助结论 + 问题清单 + 修改建议 + 人工复核提示”：

* 辅助结论可表达为 `可通过 / 不通过 / 需人工复核` 或等价枚举。
* 页面和结果 JSON 必须明确该结论是 AI 初审辅助建议，不构成正式审批决定。
* 不通过或需复核时必须列出具体不合规项、依据片段、涉及材料/字段和修改建议。
* 多处不合规必须以列表形式展示，便于课程测试用例验收。

### 13. CP3 稳定性验收

同一测试用例多次审查时，要求结构化结论一致：

* 辅助结论一致。
* 问题 code 一致。
* 涉及材料/字段一致。
* 严重程度一致。
* 自然语言说明、修改建议的措辞允许小差异，但不得改变实质含义。

### 14. 账号、角色与待办

V1 纳入正式账号、角色和待办能力：

* 不继续沿用纯匿名演示访问作为 V1 主形态。
* 需要设计登录、角色、权限边界和审批人员待办。
* 前端申请列表应从“演示环境最近申请列表”演进为按角色可见的任务列表。
* Java 后端需要成为用户、角色、任务授权和待办查询的事实源。
* 该能力属于产品化 V1 的核心目标，同时需要避免挤压 CP2/CP3 的课程硬性要求。
* 账号角色覆盖申请人、审批人员和管理员。
* 申请人登录后提交并查看自己的申请。
* 审批人员登录后查看待办并进入初审结果。
* 管理员至少负责账号/角色种子数据或基础管理能力，具体管理深度后续收敛。
* 管理员 V1 提供前端用户管理页面，支持基础用户管理和角色分配。
* 用户管理能力需要单独拆任务，避免挤压 CP2/CP3 的 RAG/MCP/Agent 主线。

### 15. 审批人员待办与基础审核动作

V1 审批人员待办包含基础审核动作：

* 通过初审。
* 退回补正。
* 转人工复核。
* 支持审批人员备注。
* 记录操作日志，至少包含操作者、动作、时间、任务、备注。

V1 不一次性引入完整正式审批流，受理、复核、办结等复杂状态可留到后续版本。

### 16. 补正与材料版本

V1 支持退回补正后的申请人补传闭环：

* 审批人员退回补正时填写补正意见。
* 申请人登录后可查看补正意见。
* 申请人补传材料后形成新材料版本，不覆盖旧版本。
* 补传后触发新一轮 AI 复审。
* 系统需要保留版本记录，用于查看历史提交、复审结果和操作链路。
* V1 需要展示材料/字段级差异对比，包括材料变更、抽取字段变化、问题新增/消失。

### 17. 审核结果导出

V1 支持导出 Word 初审报告：

* 报告内容包含材料清单、AI 初审辅助结论、问题列表、依据片段、修改建议、人工复核提示和审批人员备注。
* 报告必须明确 AI 结论不构成正式审批决定。
* Word 报告作为 CP4 答辩与产品化展示交付物。
* V1 不要求同时导出 PDF；PDF 可留作后续扩展。
* Word 初审报告由 Java 后端生成；Java 是任务、用户、材料版本、审批备注和最终结果的事实源。
* Java 报告生成只做模板渲染，不在导出时再次调用 AI。
* 推荐使用 poi-tl 基于 Word 模板生成 `.docx`；必要时局部使用 Apache POI XWPF 做底层补充。
* 报告模板固定放在 Java resources 中，例如 `src/main/resources/templates/review-report-template.docx`。
* V1 不提供管理员后台上传/替换报告模板能力。

### 18. V1 排期优先级

V1 优先先做账号/RBAC 与产品骨架，再接 CP2/CP3 AI 能力：

* 先建立申请人、审批人员、管理员账号体系。
* 先建立按角色可见的申请列表、审批待办、基础审核动作和管理后台。
* 再接入 FastAPI、知识库、MCP Server、LangChain Agent 和 Java-Python 异步审查链路。
* 风险：课程核心评分点集中在 CP2/CP3，排期时必须设置明确检查点，防止产品骨架挤压 AI 主线。

### 19. 认证方案

V1 认证采用 Sa-Token：

* Java 后端集成 Sa-Token，优先使用 Spring Boot 3 starter。
* 前端仍按前后端分离模式通过 `Authorization: Bearer <token>` 调用 API。
* 登录成功后 Java 后端签发 Sa-Token 登录 token。
* 前端通过 `Authorization: Bearer <token>` 调用 API。
* Sa-Token 负责登录态、角色校验、权限校验、踢人下线、账号禁用等鉴权能力。
* Token 续期优先使用 Sa-Token 的 `timeout` / `active-timeout` / 自动续签 / 手动续签机制，不自建 refresh token 持久化表。
* 如后续明确采用 OAuth2 授权服务器模式，再使用 Sa-Token OAuth2 的 refresh token 能力。
* V1 采用 Sa-Token 默认 token 风格，不启用 Sa-Token JWT 集成。
* Sa-Token 默认 `token-name` 使用 `satoken`；V1 前端仍统一通过 `Authorization: Bearer <token>` 传递 token。
* Sa-Token 默认 token 值风格可使用 `uuid`，即服务端有状态随机 token，而不是自包含 JWT。
* 后端 API 以 Sa-Token 解析后的用户身份做授权判断。
* V1 不采用服务端 session/cookie 作为主认证方案。
* Sa-Token 登录态接入 Redis 存储，支持跨实例登录态共享、踢人下线和权限变更生效。
* Redis 配置进入 V1 部署说明；测试环境需要提供可替代或可隔离的 Redis 配置。
* 用户密码使用 BCrypt 哈希存储，不保存明文密码。
* 申请人支持自助注册。
* 审批人员和管理员账号由管理员创建和分配角色。
* 申请人注册 V1 只做用户名/手机号唯一性校验，不接短信或邮箱验证服务。
* 任务可见性采用简单角色规则：申请人只看自己的申请；审批人员看所有待办；管理员看全部。
* V1 不做部门/区域分配，也不做任务手动派单。
* V1 前端沿用当前后台管理骨架，新增登录、注册、用户管理、待办、补正、版本对比等页面。
* 登录后根据用户角色动态展示菜单和首页内容。
* 前端动态展示只用于体验；所有权限仍必须由 Java 后端基于 Sa-Token 做强制校验。
* 每个角色有默认首页/工作台：
  * 申请人工作台展示我的申请、补正提醒和新建申请入口。
  * 审批人员工作台展示待办、风险任务和需要人工复核的任务。
  * 管理员工作台展示用户、任务和系统运行概览。
* V1 不做独立通知/消息中心；补正提醒、待办提醒只在工作台、列表和详情页展示。
* V1 申请表数据继续以上传申请书文件为主，不做在线结构化申请表填写。
* 字段结构化依赖 Python 文档解析/OCR/抽取结果，保持课程要求中的文档解析与 Agent 审查主线。
* V1 支持上传和解析 `doc`、`docx`、`pdf`、`jpg`、`jpeg`、`png`。
* Java 后端负责文件扩展名、MIME、大小和槽位校验；Python 服务负责 Word/PDF/图片解析与 OCR。
* 旧版 `.doc` 解析依赖 Python AI 服务运行环境中的 LibreOffice headless；LibreOffice 是系统依赖，通过 Docker/部署脚本安装，不作为 Python 包依赖。
* `.doc` 处理流程为 `doc -> LibreOffice headless -> docx -> Python 文档解析`。
* Python 服务需要配置 `SOFFICE_PATH` 和转换超时；转换失败要返回结构化错误，不能导致整个 AI 任务崩溃。
* Docker/部署说明需要包含 LibreOffice Writer 与中文字体安装。
* 文档解析主路径不采用 Unstructured 作为主依赖；按格式直接解析。
* `.docx` 使用 `python-docx` 提取段落和表格。
* `.pdf` 使用 PyMuPDF 提取文本和页面文本块；文本不足或扫描页由 PyMuPDF 渲染成图片后再走 OCR。
* 图片格式直接走 OCR。
* 解析后的统一文本块再进入 LangChain 分块、Embedding 和 ChromaDB。
* V1 不引入 `pdfplumber` 作为主依赖；PDF 表格不要求自动还原为二维表。若行业分类需要结构化校验，另行整理结构化字典或种子数据。
* OCR 继续使用现有 GLM OCR 作为 V1 主线方案。
* Python AI 服务沿用现有 `OCR_PROVIDER=glm`、`OCR_GLM_API_KEY`、`OCR_GLM_BASE_URL` 等配置思路，调用 GLM OCR / layout parsing 能力处理图片和扫描页。
* V1 不引入 PaddleOCR 或 Tesseract 作为主线依赖；如需离线演示或 API 不可用场景，采用预置样例结果、缓存数据或演示降级说明，而不是额外维护本地 OCR 栈。
* CP3 合规审查采用“结构化规则清单 + RAG 依据 + Agent 汇总”的组织方式。
* 结构化规则负责稳定输出问题 code、材料/字段、严重程度和基础结论，避免纯 Agent 自由发挥导致多次运行结论漂移。
* RAG/MCP 负责检索办理流程、填报说明、行业分类国标等依据片段。
* LangChain Agent 负责综合抽取结果、规则命中结果和检索依据，生成 AI 初审辅助建议、问题说明和修改建议。
* V1 不采用完全规则引擎主导的重方案，也不采用纯 Agent 自由审查作为主线。
* V1 首批结构化审查规则采用“核心初审规则集”。
* 核心初审规则覆盖材料完整性、申请书关键字段缺失、身份证/营业执照识别一致性、行业分类校验、明显格式或有效期问题、需人工复核场景。
* 申请报告、第三者利害关系说明、水资源论证、取水工程验收申请、取水工程或设施验收报告等来自 `取水许可办理需资料及流程.docx` 中的取水许可材料清单和流程说明；其中部分有样例文件，部分仅作为流程材料项出现。
* V1 不把这些扩展材料全部固化为必填上传槽位；核心规则只围绕当前固定主槽位和课程主线材料做稳定审查，扩展材料更多作为 RAG 依据、自由附件提示或 CP4 创新扩展。
* AI 审查结果采用结构化问题模型。
* 每次 AI 审查保存总结果和问题列表；总结果至少包含 AI 任务状态、辅助结论、整体说明、人工复核提示和生成时间。
* 每个问题至少包含 `code`、严重程度、材料槽位、字段、问题说明、依据片段、修改建议、是否需人工复核。
* 前端详情页展示总览卡片、结构化问题表格、依据详情和材料版本差异。
* Word 初审报告复用同一份结构化结果快照生成，不在导出时重新组织一套独立结果。
* V1 不做完整审计追溯模型；页码、文本块、检索 query、Agent 调用链路等深层追溯信息可作为调试日志或后续增强。
* Java 数据库采用“审查结果主表 + 问题明细表 + 原始 JSON 快照”的持久化方式。
* 审查结果主表记录一次 AI 审查的任务关联、材料版本关联、AI 任务状态、辅助结论、整体说明、人工复核提示、生成时间和原始 JSON 快照。
* 问题明细表记录每条结构化问题的 `code`、严重程度、材料槽位、字段、问题说明、依据片段、修改建议、是否需人工复核和排序。
* 原始 JSON 快照用于追溯 Python 回写原貌、排查问题和后续兼容字段演进。
* V1 不采用只存 JSON 的轻方案，也不采用依据、规则命中、文本块等全部拆表的重方案。
* Java 与 Python 的 AI 审查接口采用“回调为主 + 查询兜底”契约。
* Java 创建 AI 审查任务时，将 Java 申请 ID、材料版本 ID、文件访问信息、回调地址和幂等键传给 Python FastAPI。
* Python FastAPI 立即返回 `aiTaskId`、任务状态和创建时间。
* Python 完成解析、OCR、RAG/MCP 和 Agent 审查后，调用 Java 回调接口写回结构化审查结果。
* Python 同时提供任务状态/结果查询接口，供 Java 在回调失败、页面刷新、运维排查或补偿任务中主动查询。
* Java 回调处理必须幂等，同一 `aiTaskId` 或幂等键重复回写不能生成重复审查结果。
* Python 需要记录回调失败并进行有限重试；最终失败状态应可被 Java 查询或人工排查。
* Java-Python 内部接口采用内部 API Key 认证。
* Java 调 Python 创建任务、查询任务时携带内部请求头，例如 `X-Internal-Token`。
* Python 回调 Java 写回结果时也携带内部请求头，例如 `X-Internal-Token`。
* 内部 token 通过环境变量或部署配置注入，不写入 Git。
* 内部 API Key 与 `aiTaskId` / `idempotencyKey` 配合使用，分别解决服务间访问边界和重复回写问题。
* V1 不采用无认证内部接口，也不引入 HMAC 请求签名、防重放等更重的服务间认证机制。
* V1 文件访问采用对象存储方案。
* V1 直接复用 MVP 已搭建的 S3 兼容 RustFS 对象存储，不新增 MinIO 作为主线方案。
* Java 后端负责接收上传文件，并将原始材料文件写入 RustFS。
* Java 数据库保存材料元数据、对象 key、文件哈希、MIME、大小、材料槽位和版本关系。
* 创建 AI 审查任务时，Java 为每个材料对象生成短期预签名下载 URL，并传给 Python。
* Python AI 服务通过短期预签名 URL 下载材料文件，不持有 RustFS access key / secret key，不依赖共享本地目录。
* RustFS 作为 V1 复用的基础设施进入 Docker Compose / 部署说明；任务拆分时需要安排 RustFS 复用验证、预签名 URL 联调和权限边界验收。
* ChromaDB 采用 Python 服务本地持久化目录部署方式。
* Chroma 数据目录通过配置指定，例如 `CHROMA_PERSIST_DIR=./data/chroma`，在 Docker Compose 中挂载为持久化 volume。
* 知识库 ingest 命令/API 写入该持久化目录，支持重复运行、清空重建或幂等重建。
* V1 不采用内存临时 ChromaDB，也不引入独立 Chroma Server 作为主线部署形态。
* 检查点验收需要展示持久化目录、ingest 日志和统计信息，例如文档数、chunk 数、向量条目数。
* 课程资料知识库采用“文档结构优先 + 固定长度兜底”的文本切分策略。
* ingest 优先按标题、法律条款、材料清单项、表格行、填报字段说明等自然结构切分。
* 对超长文本块再按固定长度或 token 窗口切分，避免单个 chunk 过大影响 embedding 与检索。
* chunk 元数据至少保留来源文件、资料类型、章节/标题、页码或段落序号、chunk 序号。
* V1 不建设完整领域结构化知识库；材料清单、行业分类、字段说明等以文档结构化切分和元数据标注为主，必要的稳定判断通过 CP3 结构化规则清单实现。
* MCP Server 与 FastAPI 位于同一个 Python AI 服务项目中，采用两个启动入口。
* FastAPI 入口负责 Java 调用、AI 审查任务创建、后台任务执行和回调 Java。
* MCP Server 入口负责独立暴露课程要求的 MCP 工具，至少包含 `knowledge_search` 和 `check_completeness`。
* 两个入口共享底层知识库、检索、完整性检查和规则工具函数，避免实现两套逻辑。
* V1 系统实际审查链路中，LangChain Agent 在 FastAPI 后台任务内部运行。
* V1 主线实现中，FastAPI 内部 Agent 可以直接调用共享工具函数；MCP Server 独立启动用于课程演示和工具协议验收。
* 后续若需要更严格展示 Agent-to-MCP 调用链，可在不改变工具函数的前提下增加 MCP client 适配。
* CP3 结构化审查规则采用“YAML/JSON 元数据 + Python 检查函数”的实现方式。
* 规则输入是文档解析/OCR/字段抽取后的稳定事实对象，包括材料清单、申请书字段、营业执照字段、身份证字段、解析质量和检索依据。
* 规则输出统一结构化问题对象，至少包含 `code`、`severity`、`materialSlot`、`field`、`message`、`evidence`、`suggestion`、`requiresManualReview` 和 `conclusionEffect`。
* 规则元数据负责声明规则 code、分类、严重程度、目标材料/字段、提示语、修改建议模板和依据检索 query。
* Python 检查函数负责执行 required field、材料类型、跨材料一致性、OCR 质量、人工复核触发等判断。
* V1 首批规则分为材料完整性、材料类型、申请书关键字段、跨材料一致性、人工复核触发五类。
* V1 不引入完整规则引擎或后台规则管理界面；规则文件随 Python 服务版本发布，便于测试和答辩展示。
* LangChain Agent 采用“规则先行 + Agent 汇总”的执行边界。
* Python AI 审查链路先完成材料下载、文档解析/OCR、字段抽取、结构化规则检查和 RAG 检索，再调用 Agent 生成综合说明、修改建议和人工复核提示。
* Agent 不负责决定规则是否命中；规则命中由 Python 检查函数基于稳定事实对象产生，确保多次运行的问题 code、严重程度和涉及字段稳定。
* 若 Agent 调用失败或超时，系统仍保存规则命中结果，整体结论降级为“需人工复核”或等价状态，并记录“AI 建议生成失败”的结构化错误。
* V1 不采用 Agent 全权审查，也不采用多 Agent 分工主线。
* 字段抽取采用“模板/规则抽取优先 + LLM 补充兜底”的混合方式。
* 申请书优先基于 Word 表格结构、PDF 文本块或 OCR 文本布局抽取关键字段。
* 身份证、营业执照优先使用 GLM OCR / layout parsing 的结构化识别结果或文本定位结果。
* 当关键字段缺失、格式变化、OCR 文本错乱或置信度不足时，再调用 LLM 按固定 JSON schema 补充抽取。
* 每个抽取字段应记录字段值、来源材料、抽取方式、置信度或质量标记，供规则判断、版本差异和人工复核使用。
* V1 不采用纯 LLM 抽取作为主线，也不把所有格式都压到纯模板规则抽取。
* Java 侧持久化关键字段抽取快照。
* 每次材料版本审查后，Java 保存申请书、身份证、营业执照等关键字段的抽取结果、来源材料、抽取方式、置信度或质量标记。
* 前端详情页展示“系统识别信息”，用于审批人员快速核对材料内容。
* 补正后的版本差异对比复用关键字段快照，展示字段新增、变化、消失和质量变化。
* V1 不做完整字段管理模型，不支持审批人员在线编辑、确认、锁定字段值。
* 补正版本对比展示“材料 + 字段 + 问题”三类差异。
* 材料差异展示哪些材料被新增、替换、删除或保持不变，并关联材料槽位、版本号、上传时间和文件信息。
* 字段差异基于关键字段抽取快照，展示字段新增、变化、消失和置信度/质量标记变化。
* 问题差异基于结构化问题 code，展示问题新增、已解决、仍存在和严重程度变化。
* V1 不做全文级、OCR 文本级或 PDF 页面级 diff，避免页面和实现复杂度过高。
* 前端 V1 页面范围采用“角色工作台 + 核心业务页”。
* 必须页面包括登录、注册、申请人工作台、审批人员工作台、管理员工作台、我的申请列表、审批待办列表、申请详情、上传/补正、AI 初审结果、版本对比、用户管理、报告导出入口。
* 前端菜单和首页内容按申请人、审批人员、管理员角色动态展示。
* AI 初审结果、系统识别信息、补正意见、操作日志和版本差异应集中在申请详情页或其子视图中，避免拆出过多低价值页面。
* V1 不做完整后台配置页，不做知识库管理、ingest 管理、AI 任务监控、对象存储文件管理、规则配置页面。
* V1 任务拆分采用“检查点父任务 + 可并行模块子任务”。
* 父级任务按 CP1、CP2、CP3、CP4 组织，保证课程检查点验收主线清晰。
* 每个检查点尽量拆成四个人可并行承担的任务包，典型角色为 Java 后端、Python AI 服务、前端页面、文档/测试/演示集成。
* 子任务必须包含清晰交付物、验收标准、依赖关系和可演示证据。
* 任务拆分不能只按技术模块散开；每个子任务都需要映射回对应课程检查点。
* 初稿交付物范围采用“PRD + 系统设计 + V1 检查点任务清单”。
* PRD 初稿用于明确 V1 目标、范围、用户角色、核心流程、验收标准和非目标。
* 系统设计初稿用于明确 Java、Python、RustFS、ChromaDB、MCP、Agent、规则、数据库和接口的整体结构。
* V1 检查点任务清单用于按 CP1-CP4 组织四人可并行领取的任务包。
* 本轮不直接生成完整 OpenAPI、数据库 DDL、页面原型说明和部署文档全文；这些作为后续任务产出。

## Course Checkpoint Frame

* CP1：项目基础架构搭建。MVP 已基本完成，V1 做映射验收。
* CP2：知识库与 MCP Server 开发。重点是 PDF/Word 解析、文本分块、ChromaDB、语义检索、`knowledge_search`、`check_completeness`。
* CP3：初审 Agent 与系统集成。重点是 LangChain Agent、MCP 调用、docx/pdf/扫描件处理、合规审查、结果稳定性、Java 调 Python 完整流程。
* CP4：项目验收与答辩。重点是答辩说明、代码质量、README/API/部署文档、创新点。
